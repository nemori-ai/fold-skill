# 决策与待讨论问题

这份记录区分已经表达清楚的方向、尚未确认的提案，以及原稿中不再默认沿用的方案。当前是项目起步阶段；用户认可了大致方向，也明确表示细节尚未想清楚。讨论中的建议不等于已经冻结的接口。

背景见[原始设计 v0.3](reference/design-v0.3.md)。产品意图见 [product.md](product.md)，职责边界见 [architecture.md](architecture.md)，工作方式与环境见 [development.md](development.md)。

现有[用户故事](user-stories.md)、[数学模型](formal-model.md)、[信息契约](information-contract.md)与[Skill 设计](skill-design.md)用于把体验、估计和输入输出相互核对。故事中的数值、候选 JSON 字段和理想化评价式都是设计工具；它们没有冻结下列接口与实现提案。

## 已明确的当前方向

![已对齐方向、待定提案和历史参考是不同效力的材料，彼此没有自动批准或实现关系](assets/illustrations/14-design-status.png)

*方向指导设计，提案用具体场景继续收敛；原始草案保留背景，不等于当前默认实现要求。*

### 泛化输入与结构化输出构成产品边界

输入包括 Agent 自身工作、外部观测与发现、他人或用户告知。入站适配器将内容与渠道已有理解转成可共同处理的信息源表达，保留来源、时间、证据及未知。规范观测并不自动成为已接受的状态变化。

输出需要预定义结构，容纳自然语言内容，并支持排序、过滤与状态管理。Pinboard、其他 UI、基于约定信号的推送和详尽日志都是下游用途；实际发送不进入通用内核。这里确认了边界，不等于已经确定完整 schema 或实现所有消费者。

### LLM 让语境估计成为可调用的环节

数量与来源的增长扩大了整理需求；基于 LLM 的 Agent 则可以结合自然语言背景，估计用户需要知道什么、省略有什么后果、哪些表达容易误解。这是 Fold 的核心能力假设，需要通过实际场景验证，不声称估计已经准确，也不声称此前一切排序与过滤都不可行。

Skill 对语义估计的两方面帮助是转换表述与供给相关上下文。一致性既包括无关改写下保持主要判断，也包括用户背景或相关事实改变时合理调整。模型估计与执行正确性需要分别验证。

### Skill 同时交付判断指引与操作工具

Skill 需要配套一整套可调用的 CLI 或其他脚本能力，以明确动作语义承接读取、结构调整、校验、保存和结果查询。Agent 决定整理意图，程序集中处理预算算术、身份与关系维护及执行回执，减少每轮临时实现造成的操作差异。

工具的确定性保证应落在已定义的操作和约束上，不能扩大成固定的重要性策略。读取、检查、提交和查询需要形成连贯路径，失败后能分清修正声明、重读状态与核对执行结果。这里确认配套能力及职责方向；[Skill 设计](skill-design.md)中的动作族、预览、命令划分、错误结构和提交协议仍是具体提案。

### Agent 做判断，脚本守边界

重要性判断、动态份额调整，以及为了容纳新信息如何整理已有内容，主要交给 Agent。脚本负责防止低级错误、执行明确的操作，并做对齐与边界检查。有限预算仍然是约束，但不意味着脚本需要自行决定谁更重要、谁该让位。

### 信息失效与行动截止是不同概念

信息失效表达内容何时不再具有当前汇报价值；行动截止表达事情应当何时完成。账单逾期后仍可能重要，不能因为截止时间到了就推导出它应当消失。优先在 Skill 中通过说明和例子帮助 Agent 正确使用这些概念；暂不为这个区别增设一套固定的重要性或保留策略。若保留原稿的 `expires` 字段，应再明确它的含义及撤下后果，字段与触发机制尚未冻结。

### 用最佳实践培养整理能力

Skill 应帮助 Agent 理解用户怎样消费状态、如何写自足的摘要、何时覆盖或融合，以及怎样结合时间判断关注价值。示例可以提供尺度，但示例中的具体数值、顺序和选择不自动成为算法规则。

## 提案与未决问题

以下事项应在相关工作开始前逐步明确，不需要现在一次问完，也不阻塞文档与最小环境初始化。

| 建议顺序 | 需要明确的问题 | 当前提案或讨论范围 |
| --- | --- | --- |
| 定义首条跨渠道路径时 | 规范输入必须保留哪些原文、渠道解读、时间、来源与去重信息？ | 信息契约中的 Observation 是候选表达；关联、冲突、摘要加工与未知如何标注仍需收敛。 |
| 定义首个输出消费者前 | 当前状态与变化流怎样交付，哪些结构字段可稳定排序和过滤？ | 候选结构含文本、状态、来源与关注信号；重要性估计、份额和排序怎样保持一致表达，以及字段命名、版本、单位与未知值均待确定。 |
| 编写第一份 skill 前 | 估计需要读到什么、怎样表述问题与输出依据，如何检验一致性？ | Skill 设计提出读取视图及等义改写、相关背景变化、上下文缺失等对照；尚未执行模型评估。 |
| 定义首套 Skill 工具时 | 哪些动作覆盖完整整理，输入、结构效果与回执如何统一？ | Skill 设计提出操作能力与动作族；CLI 或脚本形态、命令划分、契约版本、失败恢复、操作查询及重复调用机制需一起收敛，不由 Agent 每次自行实现。 |
| 定义首个状态与操作样例时 | Agent 是否直接申报 `share`？它是否是份额的唯一来源？ | 直接申报份额是候选方案；`weight` 是否保留、作为标签还是参与计算，尚未确定。 |
| 定义首个状态与操作样例时 | 一次整理能否同时减少旧项、加入新项？失败时如何处理？ | 原子批次是候选方案，便于提交一份完整的取舍；尚未冻结批次格式与错误契约。 |
| 选择首个渲染器时 | 预算单位是什么？不同尺寸与媒介如何消费同一状态？ | 需要区分语义份额与格子、行数等表现单位；尚未决定重算份额、投影或其他适配方式。 |
| 开始首个可运行实现前 | 第一份实现用 Python 还是 TypeScript？ | 按最小闭环选择一个栈；不因原稿同时列出两个语言就同时实现。 |
| 实现时间变化时 | 已声明的信息失效由谁、在什么时候执行撤下？ | 写入时、读取时或独立时间推进都是候选触发点；需明确无新声明时状态如何变化。不能把“快失效”默认变成提前撤下的理由。 |
| 实现人与 Agent 的反馈往返前 | 用户如何分清反馈已保存、Agent 已读、展示已改与外部行动已完成？ | US-01 与 US-04 展示了这些事实的区别；具体状态名称、读取位置与结果记录机制待设计。 |
| 实现历史查询前 | 回放需要保存哪些实际变更，怎样保持反馈与来源可达？ | 数学模型给出有序事件执行的表达；存事件、存快照或结合两者尚未决定，重放不重新调用 Agent 判断。 |
| 实现详尽日志前 | 承诺保存的是整理过程，还是包括未上板观测在内的全部输入？ | 完整输入档案需要入站记录及必要原文留存；输出变化日志不能还原所有输入，保存范围与期限待定。 |
| 实现推送消费者前 | 哪些信号可触发通知，尺度、阈值与交付规则怎样约定？ | 重要性、紧急性和当前层份额分别理解；可配置阈值依赖稳定字段语义，发送、去重和结果由消费端负责。 |
| 接入并发写入前 | 多 Agent 同时整理怎么办？谁可以修改谁的条目？ | 快照版本检查、冲突后重读重提是候选机制；条目改动权限与协作约定仍待确认。并发机制不能替 Agent 裁决重要性。 |

## 原稿中不再作为默认实现要求的内容

以下设计仍保留在原稿中，供理解演进过程；未经重新讨论，不按它们直接实现：

- 固定的 `weight → share` 映射，以及同档条目必须平分某个固定份额池。
- 编译器按固定顺序自动降档、嵌套、挤出条目，以替 Agent 完成溢出取舍。
- 溢出时优先撤下临近失效的条目，或把临近行动截止等同于信息价值降低。
- 把坐标与矩形排版放进通用内核，并用某种看板的排版结果裁决通用声明是否合法。
- 起步时就交付双语言内核、全部框架适配器和远程 MCP 形态。
- 仅把 Agent 自己的工作进展视为输入，或仅把 Pinboard / 异步查看视为输出用途；当前边界已扩展为泛化输入和多应用消费。

## 用故事检验后续决定

讨论契约时，回到[用户故事](user-stories.md)中的具体结果：逾期账单是否仍可见、谁决定让位、批注是否被接住、并发更新是否丢失、历史是否能解释变化。再对照[信息契约](information-contract.md)的跨渠道例子与[Skill 设计](skill-design.md)的估计对照。它们都是设计材料，**不是已经实现或执行通过的产品测试**。

还需用首个渲染器验证：同一状态换到较小屏幕时，究竟调整预算还是仅改变呈现。满足份额总和约束，并不能单独保证矩形能排下、摘要可读或用户能迅速理解。
