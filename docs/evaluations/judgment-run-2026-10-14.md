# 判断评测：第一次真实模型运行（2026-10-14）

状态：一次性评测记录。结论只覆盖本次设置——一个情境、一个模型、一次运行、teacher-forced；不是 Skill 的验收标准，也不改变[信息契约](../information-contract.md)。

在此之前，原型情境里 112 条输入的处置和 36 个批次都由作者手写。本轮把 [skill/SKILL.md](../../skill/SKILL.md) 交给真实模型，逐帧让它读同样的状态与输入、输出处置和批次，再交给内核执行，与作者的编排对比。作者的编排不是标准答案：它是同一团队写下的一种合理整理，下文的差异案例逐一判断谁更合理。

## 结论

**能当这个编辑的初稿作者，但还不能证明它能长期独立维护这份状态。**

- **操作层面可靠。** 36 帧全部提交成功；只有 2 帧首次被拒（都是 `explicit_withdraw_required`），看到回执后一次改对。没有一次超预算，标题与摘要都在长度限制内，来源引用格式全部正确。
- **处置与档位大体一致。** 处置一致 91%；匹配上的条目里档位完全一致 48%，相差一档以内 98%，Agent 偏高 26 次、偏低 27 次，没有方向性偏差。作者自己的档位也是一次性手写，邻档差异更像两个合理编辑之间的分歧。
- **在时间与证据纪律上，几处比作者好。** 约定时间过了却没有回报时，Agent 把“已约”改成“是否到场未知，待核实”，后来的输入证明那次上门确实落空（案例 2）；零事件复核时注意到当晚的面谈只占 1 份（案例 1）；到点提醒时没有像作者那样把“已决定”写成“已回复”（案例 3）。
- **弱点在结构与身份判断。** 新信息该进已有事项还是另建，Agent 有两次把同一件事写成父项加一个新条目（案例 3、9）；它偏好扁平结构，作者在 f01 建的三层子树它没有建；撤下条目的复归用得少；无变化的复核轮次会顺手改写摘要（案例 4）；一次把“验证通过”写成“已修复”（案例 7）。
- **还没有回答的问题。** teacher-forced 每帧都从作者状态重新开始，看不到 Agent 自己的误差累积；只跑了一次，没有方差；“与作者一致”不等于“用户回来知道下一步”。这三项需要自由运行、重复运行和人工阅读来回答。

## 方法

| 项 | 设置 |
| --- | --- |
| 情境 | `prototype/scenario.mjs` 的 37 帧，由 `scripts/export-scenario.mjs` 原样导出；cold-00 没有批次，评测其余 36 帧、112 条输入。 |
| teacher-forced | 第 n 帧的起始状态 = 用 `fold/` 内核回放作者前 n−1 帧批次的结果；本帧的用户批注先用 `annotate` 存入。每帧判断彼此独立，不受模型自己的漂移影响。 |
| 模型 | `claude-opus-5-5`，`claude -p`（CLI 2.1.299），默认推理强度，结构化输出（`--json-schema`），不给工具。 |
| 系统提示 | 一句角色说明 + `skill/SKILL.md` 第一版全文（commit 012f4ad，sha256 `f0b002a2ce2f…`）。 |
| 用户提示 | `now` 与 `batch_id`；用户背景（`scenario.persona`）；业务用途与反馈约定（`scenario.feedback`，含“近期重点”与“通知中心”两种策略）；`project_state` 的完整输出；待确认批注；宿主信号（`frame.signal`，含窗口、覆盖范围与到点提醒）；本轮输入。 |
| 输入可见字段 | 事件只给 `id / channel / from / at / text`，以及宿主登记的 `feedback`（目标、动作、含义）和 `reminder`。作者的 `disposition / why / relatedIds` 是答案，不给。 |
| 输出 | `{dispositions, batch: {declarations, acknowledges}}`；新建与合并须在 `sources` 里用 `event:<id>` 引用输入。批次交给 `MemoryStore.commit`，被拒时把回执原样交回，最多再要两次。 |
| 规模 | 38 次调用，约 5.6 美元；全量只跑一次。 |

**调用方式偏离。** 任务原定用 `claude -p --bare`。`--bare` 只接受 `ANTHROPIC_API_KEY`，不读登录态，本机没有设置 API key，调用返回 `Not logged in · Please run /login`。评测改用登录态，并以 `--setting-sources ''`、`--strict-mcp-config`、`--disable-slash-commands`、`--tools ''` 和空工作目录隔离用户设置、hooks、MCP 与项目说明；同样设置下一个最小探针的输入只有约 1.1k token，说明没有额外注入的项目说明或记忆。设置了 API key 时脚本仍会加 `--bare`。

**指标怎样算。**

- 处置一致率按事件计；Agent 漏掉的事件记为 `missing`（本次没有）。
- 条目匹配：作者的 `supersedes` 与 `withdraw` 按 ID 直接匹配；作者新建与合并的条目，用 `sources` 中 `event:` 引用集合的交集匹配 Agent 的新建与合并条目（一对一贪心，同层级与标题相似度作次要依据）。只算**有效声明**：内容与原状态完全相同的补丁不改变状态，两边都排除并单列。
- 档位与 kind 只比较两边都不是撤下的匹配对。
- “终态档位”额外比较本帧结束后作者状态中每个 active 条目在 Agent 状态里的档位，用来看整体局面而不只看声明。
- 指标分别列出，不合成总分。

## 差异案例

每个案例写明作者怎么判、Agent 怎么判、我认为谁更合理，以及暴露的是 SKILL.md、情境标注还是契约的问题。

### 1. f27 零事件复核：当晚的面谈只占 1 份

- **起始状态。** 每日 08:00 整理，窗口内 0 条事件，覆盖“客户邮件、团队群与监控连接正常”。`hiring` 是 trace（1 份），`due_at` 今晚 19:30，`until_due` 11 小时 30 分钟。
- **作者。** 空批次（checked）：“本轮没有新的重要性判断，板面保持原样。”
- **Agent。** 把 `hiring` 提到 high，标题“今晚19:30面苏禾，备好职责说明”，reason 写明“招聘邮件不在本次监测范围内，时间按19日最后已知安排，暂未核实是否又有改动”；同时把已完成的发布从 critical 降到 high 让位。
- **判断：Agent 更合理。** 当晚要赴的面谈只占 1 份，用户回来大概率注意不到。Agent 还准确读出了覆盖范围不含招聘邮件，没有把沉默当成“安排不变”。这是情境标注的问题：作者在 f20 把招聘降到 trace 后，一直没在临近时复核。

### 2. f13—f15 约定的上门时间已过，却没有回报

- **起始状态。** f12 起 `home` 标题为“厨房维修已约周五14点”，`home-visit` 的 `due_at` 是周五 14:00。f13（周五 17:40）、f14、f15 的输入都与维修无关。
- **作者。** 三帧都不碰维修，状态一直写“已约”，直到 f16 物业说“昨天临时没来成”。
- **Agent。** f13 起把两项改为“原约14点上门，至今没收到到场或检查结果，待核实”，f15 写“实际是否检修、结果如何都还未收到；林苒今天在家等消息”。
- **判断：Agent 更合理，而且被后续输入证实。** 时限已过、没有观测，就不该继续写“已约”。SKILL.md 的“复核范围要广于大份额事项”在事件帧里同样生效。情境标注的问题是作者只更新与本轮输入有关的条目。

### 3. f30 到点提醒：“已决定”不等于“已回复”

- **输入。** 林苒昨晚对“苏禾提议周六10点面谈”点了“明早 09:30 再提醒”；到点提醒按时到达；林苒随后说“苏禾的电话放早上”。
- **作者。** `hiring` 改为 low / in-progress，标题“苏禾周六早上通话，已回复”。
- **Agent。** normal / needs-you，标题“苏禾面谈改周六早上电话，待回复”，摘要“未见已回复苏禾，需确认10点是否照旧”；处置里写明“稍后提醒，不算已阅，也不改截止时间”。
- **判断：在 hiring 上 Agent 更合理。** 输入只说明林苒作了决定，没有任何回复苏禾的记录；作者的“已回复”属于补全事实。
- **但 Agent 在同一帧有结构错误。** 它把 `family` 改成“明天中午去妈妈家吃面，已答应”，又在其下新建子项 `family-noodle`“周六中午去妈妈家吃面”，同一件事写了两次。作者用已有的 `family-date` 子项表达。这暴露 SKILL.md 缺少“先找已有事项再新建”的检查。

### 4. f06 重复告警与“还在查”：无变化轮次的改写

- **输入。** 同一事件再次告警、同一截图再次转发，加上周屿“还在查，晚点给结论。现在不能说是网络问题”。
- **作者。** 同内容补丁，结果是 checked，不刷新更新时间。
- **Agent。** 三条处置与作者一致，但改写了 `performance` 摘要，加入“周屿仍在查，不能归为网络问题”，结果是 commit。
- **判断：作者更贴近设计意图，Agent 的代价不大。** “不能归为网络问题”算一点新信息，但它让条目显示为刚更新，而事项没有进展。SKILL.md 只说“没有业务变化就提交空批次”，没说“确认原结论仍成立的消息只作为 used 依据，不必改写摘要”。三帧 checked→commit（f06、f14、f27）中，只有这一帧属于不必要的改写。

### 5. f01 冷启动：扁平结构、两条账单线索与被延后的随手记

- **作者。** 18 条有效声明：发布事项下建三层子树（范围、验证、旧机、回滚），财务邮件与工程私信的同额账单分成两项（“身份未核实前暂分开保留”），随手记的技术疑问留一个 trace。
- **Agent。** 6 条，全部根层：两条账单写进一项，摘要“周屿收到的2,910账单或为同一张，待核”；随手记判 deferred；根层用到 63 份。
- **判断：各有长短。**
  - 账单的处理 Agent 更省：既不重复占位，也没断言是同一张。
  - 作者保留随手记更有远见：f07 正是这条线索解释了重复后台任务。Agent 判 deferred 后，首切片里这条输入就再也取不回来（见“发现”中的输入档案）。
  - 第一帧就建三层子树是否必要，没有标准答案；但它使“新建”的匹配率只有 7/26，指标偏低主要来自这一帧。
- **情境问题：用户背景剧透了后续情节。** `persona.context` 写着“一次反复改期的招聘”，Agent 在 f01 的 reason 里写“这次招聘反复改期过”，而此时还没有任何改期。这是情境标注的问题，不是模型编造。

### 6. f10 候选人改期：撤下还是保留等待

- **输入。** 苏禾“今晚聊不了了。下周一我再给你新的时间”。
- **作者。** 撤下 `hiring`：“本周没有待决定内容；保留旧记录。”f19 再按原 ID 恢复。
- **Agent。** 保留为 low / in-progress，标题“苏禾今晚面谈取消，等下周一新时间”，理由是“需让用户知道不必赴约；之后只是等候选人回复”。
- **判断：Agent 略好。** “对方承诺下周一给时间”是一个仍在进行的等待；撤下后，如果周一没有消息，没有任何条目会提醒这一点。这是两种都合法的业务选择；SKILL.md 可以补一句：撤下前确认没有仍在进行的等待。

### 7. f12 “验证通过”被写成“已修复”

- **输入。** “旧机验证过了：连点只生成一个任务，回滚也演练了。先给远川两家开。”
- **作者。** normal / in-progress，“筛选与幂等已验证，观察两店”，reason“转入观察而非宣称永久解决”。
- **Agent。** normal / done，标题“筛选串位与重复任务已修复”。
- **判断：作者更合理。** f19 的周末日志里又出现重复任务，f23 查出另一条补偿重跑路径。旧机验证只覆盖了一条路径。值得注意的是，Agent 到 f19 看到新线索后，自己写出“幂等曾验证，周末现重复待核”。SKILL.md 的“不补全事实”只举了“预计”与“已提交”，可以补上“一条路径验证通过”不等于“问题已修复”。

### 8. f14 用户批注：当轮回应还是下一轮回应

- **输入。** 林苒对发布成果点了“收下”（ack 反馈），说想把发布块缩小，并留下批注“改到周日也可以。这次保留最大的位置给妈妈；发布做成了就让它小一点，但别删掉。”
- **作者。** 按叙事安排本帧只保存批注，空批次；下一帧 f15 才调整并确认。
- **Agent。** 当轮确认批注，把 `family` 改为“妈妈提议改周日，待你回复”并清掉原周六截止，把发布降到 low。reason 写道：“用户已阅，并要求发布完成后调小、但不要删除。按近期重点的策略保留入口；通知中心按其策略不再给它占位。”
- **判断：Agent 更合理。** 反馈与业务策略的区分完全符合[领域模型](../domain-model.md)，它在 f14 作出的取舍和作者在 f15 的取舍基本一致。“下一轮才回应”是叙事节奏，不是判断要求；类似的还有 f03（作者 f04 才确认，Agent 当轮确认）。而 f33 作者自己就是同帧确认，情境内部并不一致。

### 9. f23 新故障路径：一件事写成两项

- **输入。** 监控“DEMO-201：同一导出任务被后台补偿重跑 4 次，来源 scheduler”；林苒“别把昨天修过的那条当成回退。按新的路径写清楚”。
- **作者。** 补丁 `performance`，标题“导出补偿任务重复重跑，已暂停”。
- **Agent。** 同样补丁 `performance`，标题“前端幂等仍有效，补偿重跑待统一键”；又新建 `perf-scheduler`“补偿任务重跑导出4次，开关已关”，两项各占 12 份。
- **判断：作者更合理。** Agent 正确区分了新旧路径，也把“不影响已出报表”标为工程的说法、未核实，但同一事实占了两份关注。与案例 3 的 `family-noodle` 是同一类问题。

### 10. f26 渠道询问二十店：延后还是需要回复

- **输入。** 林苒“今天就加三家，总共五家。大家先用到周五”；渠道联系人“那我们二十家门店是不是下周就都能接了？”
- **作者。** deferred：“仍未作出该承诺，先完成五店验证。”
- **Agent。** used，新建 high / needs-you `partner-twenty`：“对方在期待承诺，若不回复或被误答，会与‘稳定前不称全面上线’的决定冲突。”
- **判断：两者都说得通，但 Agent 的份额偏高。** 对方确实在等回复，作者的写法也没有表达“需要回一句”。Agent 没有把愿望升为承诺，这一点做对了；但这件事用一句“周五后再说”就能回应，normal 足够，high 让它与当天的扩店成果同级。延后与需要回复的界线需要业务策略说明。

## 发现

### SKILL.md 需要改的地方

以下六条已写进 SKILL.md 第二版，尚未重跑评测。

1. **子层编辑的反例。** 两次拒绝都来自部分 `children` 列表。应在“子层”一节直接给出错误写法与正确写法的对照。
2. **先找已有事项，再新建。** Agent 有两次一件事两处表达（f23、f30），也倾向为子事实另建根层条目（`cost-trend`、`pilot-demo`、`pilot-hide`、`partner-twenty`）。自检清单应加一条：新建前核对 active 与 `not_active` 里是否已有同一事项。
3. **复归撤下条目。** f19 输入明说“我把你那条取消笔记翻出来了”，作者按原 ID 恢复 `reading`，Agent 没有，而是把证据写进其他条目。应提示：输入指向已撤下事项时，优先用 `supersedes` 恢复原 ID。
4. **无变化的确认。** 补一句：只确认原结论仍成立的消息记为 used，不必改写摘要；只有新增会改变用户理解的事实才更新。
5. **“验证”与“修复”。** 在“不补全事实”的例子里加入“一条路径验证通过”不等于“问题已解决”。
6. **处置与 kind 的边界。** `deferred / noise / duplicate` 的分歧集中在资讯订阅、平台统计和旧日程提醒；`kind` 一致率 72%，分歧多在“用户已决定、等待执行”（needs-you 还是 in-progress）和“结果已出、仍在观察”（done 还是 in-progress）。两处都需要可操作的判别问题，而不是更多例子。

### 情境标注的问题

1. `persona.context` 透露了后续情节（“反复改期的招聘”“家中维修”），Agent 在 f01 据此写出未发生的“反复改期过”。评测用的用户背景应只含当时已知的事实。
2. 作者有几处判断本身可商榷：f30 写“已回复”没有依据；f13—f15 的“已约”在时限过后未复核；f27 的空批次漏掉当晚面谈。
3. 批注的回应时机不一致：f03、f14 下一帧才确认，f33 同帧确认。按帧比较时，前两者会被算成分歧。
4. `deferred / noise / duplicate` 的标注缺少一致规则，例如两份资讯订阅一份判 noise（f01-e08）、两份判 deferred（f28-e03、f34-e03）。
5. f06 用同内容补丁表达“检查无变化”；契约下这等于空批次，评测按空操作处理。

### 契约与实现层面的问题（不在本轮修改）

1. **部分 `children` 列表的语义。** “目标集合”语义安全，但与模型的直觉相反，6% 的帧踩中。可选方向：保持现状、依赖明确的错误回执（本次都一次改对）；或者让嵌套 `supersedes` 只改该孩子、不改变集合，另用显式字段表达“替换子层”。这是[信息契约](../information-contract.md#补丁子层与留存)的设计问题，留给后续讨论。
2. **被延后或判为重复的输入无处可查。** f13 的“DEMO-174 事件仍未手动关闭”，Agent 判为“对不上现有事项，事件含义不明”：DEMO-174 只出现在 f06 一条被判为 duplicate 的输入里，没有进入任何 `sources`，teacher-forced 状态里查不到。f01 被延后的随手记同理。这正是[决策记录](../decisions.md#推迟到后续切片)中“完整输入档案的保存范围”的触发条件。
3. **`sources` 整组替换。** 想保留旧来源，就要在每次补丁里重抄一遍，Agent 在 f06 等帧照做了，正确但费 token，也容易漏。可以考虑追加语义或单独的“追加来源”动作。
4. **teacher-forced 的局限。** 每帧回到作者状态，Agent 自己的改动（如 f26 已把招聘提到 low）在下一帧被抹掉。它能隔离单帧判断，但无法评估累积质量。

## 还没有做的

- 自由运行：让 Agent 从 cold-01 起维护自己的状态，看误差是否累积、结构是否失控。
- 重复运行与等义改写：同一帧多次运行，以及[Skill 设计](../skill-design.md#语义估计的对照待执行)中列出的对照（等义改写、背景改变、上下文缺失、沉默与观测缺口）。
- 人工阅读：按文字简报判断“用户回来是否知道下一步”，而不是与作者逐项比较。
- SKILL.md 第二版已按上面六条修改，但没有重跑。重跑前后先比较三个数：首次提交被拒率（本次 2/36）、同一事实被写成两项的次数（本次 2 次：f23、f30）、无变化帧里的摘要改写次数（本次 1 次：f06）。2026-10-15 已在 Codex 上用两版各跑一次，见[对照评测](judgment-run-codex-2026-10-15.md)。
