# Fold：输入与输出的共同语言

状态：顶层设计稿，尚未实现。**规范化输入与预定义的结构化输出是产品方向；本文字段、枚举、数值和交付格式都是候选示例，不是冻结的 schema。** 人物与数据均为虚构。

产品动机见[产品方向](product.md)，模块边界见[顶层架构](architecture.md)，估计与执行的数学关系见[形式模型](formal-model.md)，如何教 Agent 使用这些表达见[Skill 设计](skill-design.md)。未决选择统一记录在[决策记录](decisions.md)。

## 1. 输入来自世界，输出供多个应用使用

Fold 的输入可以是 Agent 自己做事产生的进展，也可以是它观测到的告警、发现的资料、别人转告的变化或用户主动发来的消息。是否由 Agent 执行，不决定这条信息是否值得被整理。

一轮工作的基本关系是：

```text
不同渠道的原始信息与渠道语义
  → 来源适配器 → 同构的 Observation
  → Agent 结合当前状态、用户背景与反馈进行估计和整理
  → 变更声明 → 内核校验与执行 → 结构化输出
  → Pinboard、其他 UI、推送消费者、输出日志
```

| 边界 | 负责产生什么 | 不由它决定什么 |
| --- | --- | --- |
| 来源适配器 | 有来源、时间、原始内容及渠道解读的规范输入。 | 不把渠道自带的优先级直接当成用户的重要性。 |
| Agent 与 Skill | 跨来源关联、语义估计、摘要与完整取舍，提出结构化变更。 | 不把收到信息、意图或推测写成已经完成的行动。 |
| 内核与存储 | 校验并保存合法状态、明确变化及其依据，提供可读取的结构。 | 不以固定公式替 Agent 裁决关注价值。 |
| 下游消费者 | 按约定字段排序、过滤、展示、通知或记录。 | 不从份额自行推导紧急性，也不悄悄改变共享状态。 |

这里的“来源适配器”解决信息表达问题；CLI、MCP、SDK 的调用适配器解决如何调用 Fold 的问题。两者可以协作，但不是同一层职责，也不要求分别建立软件包。

共同的数据结构还需要配套的**动作契约**：每项读取或变更能力应说明操作对象、必要输入、前置条件、结构效果、保留关系、返回结果与失败含义。Skill 通过 CLI 或其他脚本调用这些能力，Agent 不必从自由文本重新推断该怎样写入数据。候选生成、校验通过与状态已保存须在结果中区分，未保存的候选不是当前共同状态；具体能力划分与恢复路径见[Skill 设计](skill-design.md)，命令名称和返回字段尚未冻结。

## 2. 规范输入保留什么

称一份规范输入为 `Observation`：**某个来源在某时提供了什么内容，以及该渠道怎样解释这些内容。** 它不是世界真相的认证，也不是已经决定展示的条目。

不同渠道需要共享一组可识别的语义位置：

- 身份与来源：能追到谁提供、从何处取得，以及可能关联哪个事项；关联尚不清楚时保留未知。
- 内容与证据：保留来源的原始陈述，或可访问的原文引用；摘要不能冒充原文。
- 来源时间：区分观测或收到的时间与事情发生的时间；未知发生时间用未知表达，不能拿接收时间补造。
- 渠道解读：解释专有术语、状态码、时间含义与范围，并标明哪些来自渠道规则、哪些是适配器的推断。未能确定的含义继续保留。

适配器可以由代码、模型或二者组合完成。其职责是让信息可共同处理；关系是否成立、不同陈述是否冲突、对当前用户有何后果，仍需要后续判断。

同构意味着字段表达一致，**不意味着各渠道已经达成语义共识**。“邮件标为高优先级”与“监控系统 P1”可以作为来源信息保留，但不能默认落在同一条用户重要性尺度上。

## 3. 两条来源如何进入同一轮整理

![两种渠道保留来源并采用同构输入，Agent 结合背景形成结构化输出](assets/illustrations/03-input-output.png)

*统一表达保留来源差别；用户计划打印，并不表示材料已经齐全。图中字段是概念示意，Agent 到输出之间省略了变更声明、内核校验与调用层保存，完整处理关系见第 1 节。*

沿用[用户故事 US-01](user-stories.md)的签证情境。签证代理发来邮件，用户随后留下一句话。以下示例使用同一 envelope；`subject_ref` 是候选关联，尚未识别到同一事项时可以为空。

```json
{
  "id": "obs-mail-17",
  "source": {"channel": "email", "author": "签证代理", "ref": "mail:17"},
  "subject_ref": "visa-trip-oct20",
  "observed_at": "2026-10-09T10:01:00+08:00",
  "occurred_at": null,
  "content": "还缺纸质银行流水，请在10月12日18点前送到。",
  "interpretation": {
    "basis": "邮件正文明确说明材料及送达期限",
    "meaning": "10月12日18点是材料送达截止，不是这条消息可撤下的时间。",
    "unknowns": ["用户是否已经准备好流水"]
  }
}
```

```json
{
  "id": "obs-user-18",
  "source": {"channel": "user_message", "author": "小林", "ref": "message:18"},
  "subject_ref": "visa-trip-oct20",
  "observed_at": "2026-10-09T10:03:00+08:00",
  "occurred_at": null,
  "content": "我下午去打印，原定10月20日的出差照常。",
  "interpretation": {
    "basis": "用户陈述；按消息日期解读“下午”",
    "meaning": "用户计划今天下午打印，并确认出差安排仍有效。",
    "unknowns": ["打印是否实际完成", "材料是否已送达"]
  }
}
```

`content` 在这里是原始短消息；大附件可改用原文引用与明确标注的摘录，具体保存方式待定。两个 `occurred_at` 都为空，避免声称已经知道缺材料从何时开始，或打印已经发生。

Agent 将两条输入放在一起，并读取已有状态、出差背景与其他待关注事项，才形成当前判断：材料仍缺，但用户已有准备计划；需要保留提醒，摘要应说清剩余动作。重复收到邮件不意味着新建第二个签证条目；用户的打印意图也不意味着可以把材料标为齐全。

## 4. 输出的结构让判断可以被复用

输出需要预定义结构，使消费者能可靠地定位条目身份、文本、关系、估计、状态、来源与变化。自然语言适合承载摘要和判断理由；排序、过滤与状态管理所依赖的概念需要有约定的位置和含义。

下面将一份简化快照与一条变化记录放在一起，只展示可能的表达。不规定必须采用 `snapshot`、`changes` 两个顶层字段，也不规定估计必须使用这些标签。示例变化记录未展开完整重放数据，不能直接当作重放协议。

```json
{
  "snapshot": {
    "revision": "r12",
    "root": {
      "budget": 64,
      "items": [{
        "id": "visa-materials",
        "title": "签证材料仍待补齐",
        "summary": "你计划今天下午打印银行流水；需在10月12日18点前送达，尚无完成确认。",
        "status": "awaiting_materials",
        "importance": {"estimate": "high", "basis": "影响仍有效的10月20日出差计划"},
        "urgency": {"estimate": "time_sensitive", "action_due_at": "2026-10-12T18:00:00+08:00"},
        "attention": {"share": 24, "rank": 1},
        "validity": {"withdraw_after": null},
        "source_refs": ["obs-mail-17", "obs-user-18"]
      }]
    }
  },
  "changes": [{
    "item_id": "visa-materials",
    "kind": "updated",
    "reason": "纳入代理的材料期限与用户的打印计划，仍保留未完成事实。"
  }]
}
```

此例只有一个条目，预算其余部分留白；`24` 不来自固定换算表，也不表示重要性有精确的绝对量值。真实整理须比较当时的完整状态。

这些输出维度需要分开解释：

| 维度 | 回答的问题 | 不能直接推导什么 |
| --- | --- | --- |
| 重要性估计 | 这件事影响用户目标或决策有多大？ | 不直接等于处理时限或通知许可。 |
| 紧急性估计 | 推迟获知或行动会有什么影响？ | 临近时间不自动等于高紧急，也不等于信息失效。 |
| 注意力份额 | 当前这层应该为它分配多少关注？ | 不是紧急性、概率或通用推送分数。 |
| 排序 | 当前消费范围内按什么维度、先呈现哪项？ | 不能无说明地颠倒状态表达的关注顺序；状态排序与份额的关系，以及消费者按其他字段排序的规则需明确约定。 |
| 行动状态与时间 | 事情到哪一步、何时需要完成？ | 截止已过不推出已经完成或应该撤下。 |
| 信息有效性 | 依据何时不再适用、是否有明确撤下声明？ | 不能从一个日期无条件推出。 |

这些维度是否都成为独立字段、如何定义尺度和解释未知值，尚待场景验证。Skill 要帮助模型给出有依据、可修正、表达稳定的估计，而内核检查结构与已约定边界；内核校验通过不证明语义估计准确。

## 5. 同一输出可以有哪些消费者

- **Pinboard 与其他 UI：** 使用稳定身份、摘要、层级与份额展示当前局面，保留来源与变化查询入口。
- **推送消费者：** 在字段含义、估计尺度及用户配置明确后，按约定的紧急性或重要性阈值筛选，再结合自己的发送与去重规则。序数标签也可以有约定顺序，无须假装成精确数字；目前尺度与阈值尚未校准。真正发送、发送许可及送达结果由消费者负责，内核不负责发通知。
- **输出日志：** 按序记录每次已接受的变化，必要时附快照，供细查 Agent 当时如何调整状态。它能比当前视图详细，但只覆盖实际留下的输出记录。

不能从有损的当前状态或变化日志还原所有原始输入。若产品要求“任何收到或观测到的信息都能查”，必须另行保留入站 Observation 流及必要的原文存档，并明确存档范围；输出日志与完整原始输入日志是两种承诺。

## 6. 三条必须保留的边界

![输入观测记录与已接受状态事件分别保存，校验失败返回修订而不改变已接受状态](assets/illustrations/11-incoming-vs-committed.png)

*两类记录回答不同问题；输入留存范围待定，不能从状态历史反推出全部原文。图中 10:01 与 10:03 对应前述两条输入的观测时间 `observed_at`，不是事情发生时间。*

**Observation 不等于已接受的状态事件。** 输入可能被关联、暂缓、判为重复或因冲突暂不采纳；状态事件只记录已经决定并通过执行校验的变化。校验不通过时，错误返回 Agent 修订声明；被拒绝的变化不进入已接受的状态记录，也不改变当前状态。

图中的输入记录回答“收到了什么”，状态记录回答“接受了哪些变化”；两者分开表达，不要求立即采用两种数据库。若选择通过状态事件重放，记录须包含重建状态所需的数据，并按接受的顺序应用；不能直接重放输入记录，也不应重新调用模型解释原始消息。输入记录的保存范围及事件与快照的组合方式仍待设计。

**说了什么不等于做成什么。** 用户反馈和 Agent 自身进展都可进入同一种规范输入，但“用户说已付款”“系统确认付款”“Agent 已读留言”是不同事实。反馈保存、读取确认、展示调整及外部行动结果仍须分别追踪，不能被一个通用 `status` 混为一谈。

**消费者的投影不等于新的共同状态。** UI 过滤或推送筛选只影响该消费者的结果；若要改变共享条目及重要性，应提交明确变更并进入相同的判断与执行流程。

下一步应选择一条跨渠道输入、一次上下文估计和至少两种输出消费的完整样例，用它收敛具体字段、尺度与保存范围；这些接口尚未在本轮实现。
