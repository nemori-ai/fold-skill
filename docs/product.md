# Fold：产品方向

状态：首切片设计基线的一部分，产品待实现。本文解释产品意图；外部行为见[信息契约](information-contract.md)，范围与后续问题见[决策记录](decisions.md)。

## 为什么做

当多个 Agent 持续替人工作，工作进展、外部观测与发现、别人或用户告知的消息都会不断进入它们的上下文。这些信息加在一起，可能超过一个人的注意力。用户还得阅读、比较、去重，并判断现在需要自己做什么。

Fold 让 Agent 完成这部分整理：把来自不同渠道的信息，结合当前状态和用户处境，归约为一个有预算、按重要性表达、持续更新的结构化状态。

核心设计假设：**LLM 在增加信息规模的同时，也让跨语境的重要性、延后后果与表达价值估计成为可调用的能力。** 我们借此判断“用户下次接触这些信息时，什么会改变其理解或行动”。这个假设通过场景验证。

![LLM 同时增加多源信息的整理需求，并提供结合语境估计关注价值的能力](assets/illustrations/07-why-llm-now.png)

*Fold 的设计假设：LLM 既增加待整理的信息，也提供理解语境、估计关注价值的能力。*

Skill 帮助估计的两个方面是：把问题与事实转换成一致、可比较的表述，让 Agent 看见相关状态、目标、偏好与反馈。见[skill 设计](skill-design.md)。

用户可以在方便的时候回来掌握局面，下游应用也可以根据同一输出组织界面、通知或日志。期望建立的是：**我知道哪些信息值得关注，也能理解这些信息为何出现在面前。**

“人离开半天再回来”是首个验收场景，人在场时也可以持续消费整理后的状态。需要立刻告知的事项先走即时渠道，再判断哪些结果、待办或背景仍有持续关注价值，应当纳入 Fold。

## 当前设计原则

- **预算属于信息接收者。** 为同一个人服务的多个 Agent 共享预算，各自精简不等于整体精简。
- **预算促使 Agent 做取舍。** 新增、覆盖、合并、嵌套、撤下都应服务于当前的汇报需要；允许留白。
- **档位表达关注价值，份额默认由档位派生。** 内容多不意味着重要；Agent 结合用户处境比较后给出档位，脚本换算为份额，必要时允许附理由作例外分配。
- **来源可以不同，判断需要共同上下文。** 渠道把信息及已有解读转成统一表达，保留出处与不确定性；某个渠道的标签不直接决定全局重要性。
- **先理解要点，细节按需展开。** 摘要让人理解当前局面；需要进一步了解时，再获取相关细节与依据。每一层都约束需要同时关注的信息量。
- **当前状态会被整理，变化可追溯。** 用户能理解某件事为什么被简化表达、与其他内容合并，或暂时不再出现在当前汇报中。
- **人可以轻量反馈。** 用户留一句批注，Agent 在后续工作中读取、理解，并在整理中确认。保存、处理确认和外部行动结果是不同事实。

![先理解当前要点，需要时再获取相关细节与依据](assets/illustrations/05-attention-and-detail.png)

*先用摘要掌握当前局面，再按自己的需要深入了解。*

针对其中一个要点继续追问时，相关细节可以包括背景、判断依据和待确认事项。它们围绕这个要点展开，摘要本身仍应让人理解当前局面。

## 从具体场景开始

[用户故事](user-stories.md)用五个情境展开这种体验：离开半天再回来、账单逾期与报价失效、满额时出现更重要的事情、用户更正偏好，以及多 Agent 更新后追查某条内容的去向。

首切片实现 US-01 的完整往返：工作产生进展，Agent 整理状态，用户回来查看并批注，Agent 接住后再更新实际结果。首切片的输入是 Agent 自己的声明，面向人的首个输出是文字简报；Agent 还可以按需取得静态状态概览，辅助阅读结构化状态。

重新检查没有发现变化，也是一种有意义的结果：系统让人知道检查发生过，不把检查时间当成内容更新时间。补充来源是一种资料更新，但不自动证明事情向前推进；呈现应说清楚变了什么。

[数学模型](formal-model.md)进一步描述状态、预算与 LLM 语义估计，并区分可检查的约束与估计质量。每层预算有上限，不等于用户连续展开的总阅读成本有固定上限。

## 从信息来源到下游用途

Fold 的输入既可以是 Agent 的工作结果，也可以是一次外部观测，或用户说的一句话。入站适配器把它们转成同构的信息源表达，保留原始内容或引用、渠道已有解读、来源、身份、时间与不确定性。统一格式便于一起处理，不表示内容已经被证实。

Agent 判断时会结合多种信号，包括来源陈述与渠道解读、用户目标与偏好、当前状态、时长投影及已有反馈。它在共同语境中估计哪些信息会影响用户的理解或行动，决定怎样取舍与表达，再由脚本验证并执行这些明确变化。

输出是一份遵循预定义结构的状态与变化，其中包含自然语言摘要与理由，供下游排序、过滤和状态管理使用。字段见[信息契约](information-contract.md)。

例如，用户说“这篇文章是明天讨论要用的”，外部观测又发现“原机票报价已失效”。两者进入同一种输入表达，保留各自出处；Agent 在共同上下文中重新估计，保留讨论材料，并更新机票的当前状况。同一份输出可供不同下游使用：

- **文字简报（首个消费者）：** 优先呈现主要事项，折叠次要内容，保留细节与历史入口；具体呈现规则见[信息契约](information-contract.md)。
- **Agent 状态概览（首切片可选）：** 用精简 Pinboard 补充 state JSON：同层份额越大，占据的面积越大；颜色、边框和标记表达状态与变化。Agent 选择内容，工具布局并真实截图，标明版本、真实留白和未展示内容；精确值仍可查对应 JSON，不添加新事实或修改状态。
- **Pinboard 或其他 UI（后续）：** 把份额映射为面积，按层级和媒介特性组织阅读；完整交互界面不在首切片内。
- **推送应用：** 按用户配置的策略筛选值得通知的变化，避免从面积直接推导是否打断用户。
- **日志应用：** 展示谁在何时依据什么改变了状态，供追查与复盘。

推送的实际发送由下游应用负责，通用内核不承担发送动作。详尽日志保存结构化变更历史与来源引用；仅保存有损摘要不能恢复全部输入。

静态概览是所选范围内的等价视觉表达，由真实 HTML/DOM 渲染后截图，属于辅助 Agent 读状态的小工具。输入选择、导出产物和差异范围统一见[信息契约](information-contract.md)。

## 成功信号

- 用户在短时间内辨认出需要自己处理的事，也知道其余事项的主要进展；“约一分钟”是初期观察目标。
- 同一件事的新进展替换了旧进展，用户无需自己从多条汇报中拼出当前状态。
- 父层摘要足以理解结果或下一步，展开是用户的主动选择。
- 用户批注被接住，之后的状态能体现实际处理结果，或明确说明仍待处理。
- 同一批次因回执丢失而重试，不会重复新增条目或批注；没有内容变化的复核不会伪造新的进展。
- 用户能解释重要性的分配，并能通过反馈纠正它。
- 来源措辞等无关变化不会无故颠倒主要取舍；用户目标或相关事实改变时，估计能合理调整。

## 当前非目标

- Fold 不承担任务执行、工作调度或完整任务管理；批注可能引发行动，但行动由 Agent 所在的系统负责。
- 通用内核不发送消息，也不根据条目面积自动决定是否打断用户。
- 启动阶段不承诺同时交付多语言内核、MCP、各框架 SDK 和多种界面。

## 核心术语

| 术语 | 当前含义 |
| --- | --- |
| 规范信息源表达 | 来自不同渠道的信息及其解读，用共同结构表达，保留来源与未知。后续切片。 |
| 语义估计 | 结合事实、当前状态与用户处境，估计关注价值、表达价值及延后或省略的后果。 |
| 状态 | 经整理后的结构化结果，供界面、推送策略或日志等下游消费。 |
| 条目 | 状态中的一个汇报单元，可关联细节、来源与批注。 |
| 层 | 一组共享预算的条目；条目可包含下一层。 |
| 预算 | 一层允许占用的注意力总量，首切片 B = 64。 |
| 档位 | Agent 给出的五档相对关注价值：critical / high / normal / low / trace。 |
| 份额 | 默认由档位派生的预算占用量；可用 `share` 与 `reason` 明确覆盖。 |
| 声明 | Agent 提交的一条条目意图；一次整理是一个批次。 |
| 批注 | 用户留下的文字反馈；记录反馈不等于已经完成其中的行动。 |
| 处理确认 | Agent 已在整理中确认或回应某条批注；不等于外部行动完成。 |

批次身份、状态版本、字段与操作规则统一定义在[信息契约](information-contract.md)。
