## 原则

- **Agent 的批次是底稿。** 只在三种情况下改：判断会误导读者（该等你的被记成知会、不相关的事并成一件、长期占着最大份额）；语料版本差异让 Agent 写错了事实；份额腾挪是上面两类修正的连带结果。措辞偏好、可以接受的档位分歧都不改。
- **只改批次，再重放。** 修正写成对批次的 `patch`、`replace`、`add`、`drop`，重放被内核拒绝就停下；腾份额时优先提前撤下 Agent 自己后来也撤下的痕迹，并沿用它的理由。
- **不改原文。** MIX.md“接缝”一节列的不一致（公寓与房子、住在法国、北美的电气习惯、2001 年的营销内容、问的是狗而人物养猫）不改输入，影响理解时在旁白里带一句。
- **回应路径与反馈是演示数据先行定下的形态**（见[原型说明](../../README.md#演示数据)），不是 Agent 的输出：ask 由打磨时登记，反馈从本人的真实后续动作推出。

- 对 Agent 批次的修正 31 处，分布在 18 帧：其中 14 处是同一个判断（master CI 的档位）在 f11 之后逐帧延续；另有 1 处手写反馈链接。处置（`disposition`）没有改。
- 登记回应路径 20 条：approve 6、choose 5、reply 4、schedule 2、defer 2、confirm 1；其中 7 条在窗口内被本人在来源处的动作回答，13 条到最后仍开着。
- 反馈链接 157 条，挂在 154 条本人输入上：31 条指回具体的 ask，126 条只指向事项（那件事当时没有登记问题）。

## 最常见的三类错误

按自由运行的全部 28 帧数，不只是被修正的那些：

1. **生活里要他决定的事被低估。** 根层 64 份平均只有 13.1 份来自生活流，工作流 48.9 份；生活流里本人后来有行动的事项帧 61 个，Agent 纳入 45 个，但只有 2 个拿到 6 份以上。最明显的是航班改经停（f08 记成知会 3 份，f10 降到 1 份，f11 在改签选项还开着时撤下）、车道下漏水的主水管（f26 只给 3 份）、热浪里的空调（f25 只给 1 份）。猫的药量是反例：f18 给 6 份，看到“超过 5 mg/kg 有失明风险”后 f22 主动升到 12 份。
2. **长期事项一直占着大份额。** master CI 从 f02 到 f28 共 27 帧都是“等你”、12 份，期间别人在修、他做的是评审与合并修复；弱标注把这条线判为 noise 或 delegated。另有每天一条“今日合并了什么”的 done 记录，以及几件一周没有动静、只占 1 份的痕迹，在根层留成长尾（同一时刻最多 33 件，两周出现过 88 件根层事项）。
3. **把不相关的提问并成一件。** 同一个半天里本人发的几个生活提问，Agent 三次各并成一件：自行车异响与 Hebel 墙固定（qa-life-0803）、贝壳熬汤与猫在花盆里排便（qa-life-0808）、TPU 气嘴、老车架上的孔与女儿的漫画（qa-life-0811）。标题能看出是两三件事，但份额、问题与反馈都只能挂在一起。

此外，提交被退回的 5 次都是操作层面的问题（摘要超长、超预算），回执说明后一次改对，不影响演示数据。

## 语料版本

自由运行开始时语料是 v1（`frames.json` sha256 `8fc68096…`），跑到第 12 帧时语料更新到 v1.1（`7c60cb32…`）。按协调约定，已过 5 帧不重跑，演示数据以 v1.1 为准：

- **21 条别人的回答与评论在 v1 里署名成本人**（作者栏写成 `Jonas B.`，`self` 仍为 false），出现在 f05、f10、f14、f15、f16、f20、f22、f23、f26、f27、f28 共 11 帧。逐条核对 Agent 引用它们的事项：f05–f06 的自行车异响、f14–f16 的帽檐与毛巾杆、f16 的公路旅行、f27–f28 的修车价，Agent 都按 `self: false` 当成别人的话，写成“你……”的句子都有真实的本人评论支撑；只有 f26 的空调把作者写成了“Jonas B.名下新答”，已按 v1.1 改为 Maja Zeller。
- **4 条博客评论换了 ID**（f24）：edits.json 的 `renamed_events` 把 Agent 处置与引用里的旧 ID 换成新 ID。
- **约 120 处正文修补了化名遗漏**，以及链接锚点与跟踪串的化名：演示直接用 v1.1 的正文与链接，Agent 的判断不受影响。

## 回应路径与反馈

- **登记。** edits.json 的 `asks` 按事项与帧登记，按钮从模板来（review → approve，issue → choose，answer → reply，confirm、schedule、defer），也可以直接写；可选的 `short` 是 16 字以内的短问法，供腕上一瞥。ask 属于登记时的条目版本：条目此后每被改写一次就以同一 id 重登记，直到 `until` 或条目不再 active；改写后没有重登记的，视为问题失效。
- **反馈从真实动作推出。** 本人在 GitHub 上的评审、合并（含“closed this in 提交”）、关闭，以及在论坛、问答站、邮件列表、Mastodon 上的回复，按线程挂到当时引用了同一线程的 active 事项上，`via` 记为 `source`。那件事登记着 ask 时，动作映射到 ask 的按钮（合并算批准）；没有对应按钮或没有 ask 时只指向事项，动作取自 `feedback.sourceActions`。
- **例外。** 公路旅行的提问登记的是“Tilda 问你只要美国的方案吗”，他后来的几条回复都是回给别人的，所以这条 ask 设 `link_source: false`，回复只记在事项上，问题保持开着。
- 7 条被回答的 ask：水碗尺寸、#13473、#13481（undef）、vdns、航班信息、#13528、#13572。到最后仍开着的有 #13350 的复审、猫的药量（两次登记）、车道下的水管、Tilda 的提问与后刹排气等，演示里能看到问题一直悬着、也能看到改写后悄悄失效（航班的“约时间打给 LH”）。

## 旁白、章节与信号

- 每帧的 `title` 与 `narrative` 由打磨时按输入与 Agent 的批次手写，提到 Agent 原判断与打磨改动的地方都直接说明。
- 6 章按日期与主线分：漏洞报告重开与 NDEBUG 之争、最忙的一天撞上航班改经停、rc1 与功能冻结、猫的药量与 NTLM 复用、热浪与车道下的水管、周日收尾。
- `frame.signal` 保留 Agent 看到的宿主信号（每 12 小时定时整理、收到条数与窗口），另加 `coverage` 写各流条数，并注明这一帧有几封营销邮件没有收入演示（所以 `received` 可能比演示里的输入多）。
- 第二轮草图的选用帧写在 `sketchFrames`，说明写在 `sketchNotes`。
- 根层事项的短名写在 `categories.<id>.short`（89 件，手写）：取标题里的事（“猫的药量”“主水管”“NTLM 复用”），不用 PR 编号；让位图与批次记谱在色块和记号旁用它。没写短名时脚本退回编号或标题首词。
